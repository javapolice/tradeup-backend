# TradeUp MVP 요구사항

이 문서는 Phase 1 MVP의 도메인 규칙과 Phase 1.5에서 추가한 인증·인가·입력 검증 요구사항을 함께 정리한다. 현재 상태는 **Phase 1.5 구현 완료·최종 문서화 및 정리 중**이다. HTTP 요청·응답의 상세 계약은 [API 명세](api-design.md), 도메인 상태 전이는 [도메인 모델](domain-model.md)을 따른다.

## 1. 프로젝트 목표

대규모 트래픽과 실제 운영 이슈를 단계적으로 재현하고 해결하며,

최종적으로 AI Agent 기능까지 확장하는 중고거래 플랫폼 백엔드 프로젝트를 개발한다.

서비스 기능 자체를 많이 구현하는 것보다

백엔드에서 발생할 수 있는 문제를 재현하고 해결하는 과정을 증명하는 것을 우선한다.

## 3. MVP 사용자 흐름

회원은 이메일·닉네임·비밀번호로 가입하고 이메일·비밀번호로 로그인하여 JWT Access Token을 발급받을 수 있다.

인증된 회원은 JWT를 전달하여 판매할 중고 상품을 등록할 수 있다. 판매자 ID는 인증된 회원으로 결정된다.

사용자는 등록된 상품 목록을 조회하고 특정 상품의 상세 정보를 확인할 수 있다.

현재는 상품 단건 및 판매 중인 상품 목록을 조회할 수 있다. 조건 검색은 미구현이며 향후 검토 대상이다.

사용자는 관심 있는 상품을 찜하거나 찜을 취소할 수 있다.

사용자는 판매 중인 상품에 대해 구매를 요청할 수 있다.

거래가 정상적으로 완료되면 해당 상품은 판매 완료 상태가 된다.

## 4. Phase 1·1.5 유스케이스 및 비즈니스 규칙

### 공통 인증·인가

- 공개 업무 API는 회원가입, 로그인, 상품 목록, 상품 단건 조회 4개이다. 나머지 업무 API 13개는 JWT 인증이 필요하다.
- 보호 요청에는 `Authorization: Bearer <accessToken>`을 전달한다. 서명·만료 검증 후 JWT의 회원 ID가 principal이 된다.
- 상품 판매자, 찜 등록자, 거래 구매자와 상태 변경 요청자는 principal로 결정한다. body/query로 인증 주체의 sellerId·buyerId·memberId를 지정하지 않는다.
- 회원 정보·찜 목록·구매 내역은 경로 memberId와 principal이 같은 경우에만 조회할 수 있다. 상품 거래 이력은 해당 상품 판매자만 조회할 수 있다.
- 인증이 필요한 요청에 토큰이 없거나 유효하지 않으면 401, 인증 후 본인·판매자·소유자 조건을 위반하면 403으로 거부한다. 잘못된 Bearer 토큰을 제공하면 공개 API도 401이 된다.
- 현재 Refresh Token, 로그아웃, 토큰 폐기 API는 없다. JWT 인증은 stateless 방식이며 이후 권한 검사는 별도로 수행한다.

### Member

#### 회원 가입

회원은 이메일·닉네임·비밀번호를 사용하여 가입할 수 있다.

비즈니스 규칙 :
- 이메일은 중복될 수 없다.
- 닉네임은 중복될 수 없다.
- 가입 비밀번호는 BCrypt 해시로 저장한다. 비밀번호·해시는 회원 응답에 포함하지 않는다.
- 이메일은 필수·이메일 형식·최대 255자, 닉네임은 필수·최대 255자이다. 비밀번호는 필수이다. 세 값 모두 null·빈 문자열·공백만 있는 값은 거부한다.

#### 로그인

이메일·비밀번호는 각각 비어 있지 않아야 한다. DB 회원의 BCrypt 해시와 비밀번호를 비교한 뒤 `accessToken`, `tokenType`(`Bearer`)을 반환한다. 현재 Access Token 유효기간 설정은 3,600초이다.

존재하지 않는 이메일, 비밀번호 불일치, passwordHash가 null인 기존 회원은 동일한 로그인 실패 메시지와 401을 반환한다. 비밀번호 재설정·기존 회원 해시 보완 기능은 현재 없다.

#### 회원 조회

인증된 회원은 자신의 회원 ID에 해당하는 정보만 조회할 수 있다. 응답에는 id·email·nickname만 포함하고 비밀번호·해시는 포함하지 않는다.

### Product

#### 상품 등록

회원은 판매할 상품을 등록할 수 있다.

상품은 다음 정보를 가진다.

- 제목
- 설명
- 가격
- 판매자
- 상품 상태

비즈니스 규칙 :

- 상품 최초 상태는 `SELLING`이다.
- 상품은 하나의 판매자를 가진다.
- 판매자는 JWT principal로 결정한다. 제목은 필수·공백만 있는 값 불가·최대 255자, 설명은 선택·null 또는 최대 255자 문자열, 가격은 필수·0 이상 Long 값이다.

#### 상품 조회

사용자는 상품 단건을 조회할 수 있다.

사용자는 판매 중인 상품 목록을 조회할 수 있다.

#### 상품 수정

판매자는 자신이 등록한 상품을 수정할 수 있다.

비즈니스 규칙 :

- 판매자 본인만 수정할 수 있다.
- `SELLING` 상태의 상품만 수정할 수 있다.
- PATCH는 요청한 필드만 변경하고 미전달 필드는 유지한다. 최소 한 필드를 포함하는 객체여야 한다.
- 제목은 null·빈 문자열·공백만 있는 값이 불가하며 최대 255자 문자열이어야 한다.
- 설명의 명시적 null은 기존 설명 삭제, 빈 문자열은 빈 문자열 저장을 뜻한다. 문자열은 최대 255자이며 미전달과 null을 구분한다.
- 가격은 0 이상 Long 범위의 JSON 정수만 허용한다. null·음수·소수·지수 표기·숫자 문자열·잘못된 자료형·범위 초과는 거부한다.
- 알 수 없는 필드와 빈 객체는 거부하며 여러 필드를 동시에 수정할 수 있다. 상세 자료형·오류 규칙은 [API 명세](api-design.md)의 PATCH 절을 따른다.

#### 상품 삭제

판매자는 자신이 등록한 상품을 삭제할 수 있다.

비즈니스 규칙 : 

- 판매자 본인만 삭제할 수 있다.
- `SELLING` 상태의 상품만 삭제할 수 있다.
- Trade 상태와 관계없이 거래 이력이 하나라도 있으면 삭제할 수 없다.
- Trade 이력이 없고 Wishlist만 있으면 관련 Wishlist를 먼저 삭제한 뒤 Product를 삭제한다.
- Trade는 비즈니스 이력이므로 cascade 삭제하지 않는다.

### Wishlist

#### 상품 찜

회원은 관심 있는 상품을 찜할 수 있다.

비즈니스 규칙 :

- 자신의 상품은 찜할 수 없다.
- 동일 회원이 동일 상품을 중복으로 찜할 수 없다.
- 등록 회원은 principal로 결정하며 본문에는 productId를 전달한다. 현재 찜 등록에는 상품 판매 상태 제한이 없다.

#### 상품 찜 취소

회원은 자신이 등록한 찜을 취소할 수 있다.

다른 회원의 찜을 삭제하려 하면 거부하며 기존 찜을 유지한다.

#### 찜 목록 조회

회원은 자신이 찜한 관계 목록을 조회할 수 있다. 경로 memberId가 principal과 다르면 거부하며, 결과는 상품 상세가 아닌 Wishlist 응답 배열이다.

### Trade

#### 거래 요청

구매자는 판매 중인 상품에 거래를 요청할 수 있다.

비즈니스 규칙 :

- `SELLING` 상태의 상품에만 거래를 요청할 수 있다.
- 판매자는 자신의 상품에 거래를 요청할 수 없다.
- 최초 거래 상태는 `REQUESTED`이다.
- 같은 상품에 여러 구매자가 각각 거래를 요청할 수 있다.
- 같은 구매자는 같은 상품에 활성 `REQUESTED` 요청을 중복 생성할 수 없다.
- `REJECTED` 이력이 있어도 Product가 `SELLING`이면 새 Trade로 재요청할 수 있다.
- 구매자는 JWT principal로 결정하며 본문에는 productId를 전달한다. 찜·거래 요청의 productId는 필수이며 양수 Long 값이어야 한다.

#### 거래 요청 수락

판매자는 자신의 상품에 들어온 거래 요청을 수락할 수 있다.

비즈니스 규칙 :

- 판매자만 거래 요청을 수락할 수 있다.
- `REQUESTED` 거래이며 상품이 `SELLING`인 경우에만 수락할 수 있다.
- 거래 상태는 `ACCEPTED`가 된다.
- 상품 상태는 `RESERVED`가 된다.
- 같은 상품의 나머지 `REQUESTED` 거래는 모두 `REJECTED`가 된다.

#### 거래 요청 거절

판매자는 자신의 상품에 들어온 거래 요청을 거절할 수 있다.

비즈니스 규칙 :

- 판매자만 거래 요청을 거절할 수 있다.
- `REQUESTED` 거래만 거절할 수 있으며 상품 상태는 변경하지 않는다.
- 거래 상태는 `REJECTED`가 된다.

#### 거래 완료

수락된 거래를 완료 처리할 수 있다.

비즈니스 규칙 : 

- `ACCEPTED` 상태의 거래만 완료할 수 있다.
- 상품은 `RESERVED` 상태여야 한다.
- 현재 MVP에서는 상품 판매자가 거래 완료를 처리한다.
- 거래 상태는 `COMPLETED`가 된다.
- 상품 상태는 `SOLD`가 된다.

#### 거래 조회

회원은 자신이 구매자로 참여한 거래를 조회할 수 있다.

상품 ID로 해당 상품의 전체 거래 이력을 조회할 수 있으며 인증된 판매자 본인만 허용한다. 구매자·무관한 회원의 조회는 거부한다. 구매 내역은 경로 memberId와 principal이 같아야 한다.

Phase 1의 거래 규칙은 정상적인 순차 요청 흐름을 보장하는 수준이다. 동시 요청에 대한 완전한 정합성 보장은 Phase 3에서 다룬다.

## 5. 도메인 책임

### Member

회원 식별과 비밀번호 해시의 보관 주체이다. 비밀번호 비교·토큰 발급·요청 인증은 Service·JWT 구성요소에서 처리한다.

회원은 상품의 판매자 또는 구매자가 될 수 있다.

### Product

판매자가 등록한 중고 상품을 관리한다.

상품명, 가격, 설명 및 판매 상태 등을 가진다.

상품 조회의 중심 도메인이다. 조건 검색은 아직 구현하지 않았다.

### Trade

상품의 실제 거래 과정을 관리한다.

판매 상품과 구매자를 연결한다.

거래 요청, 수락, 거절, 완료 등의 상태를 관리한다.

상품 상태와 거래 이력을 분리하여 관리한다.

### Wishlist

회원과 관심 상품의 관계를 관리한다.

회원은 하나의 상품을 찜하거나 찜을 취소할 수 있다.

## 6. 초기 MVP에서 제외하는 기능

아래 제품 기능의 제외 방침을 유지한다. N+1 최적화·동시성 제어·캐시·비동기·AWS·부하 테스트·AI Agent는 별도의 [후속 Phase](roadmap.md) 계획이며 현재 구현 완료 기능이 아니다.

- 실시간 채팅

- 실제 결제

- 배송

- 신고

- 관리자 페이지

- 쿠폰

- 실시간 알림

위 기능들은 이후 백엔드 기술적 문제를 증명하기 위해 필요한 경우에만 추가한다.

## 7. 프로젝트 핵심 원칙

기술을 사용하기 위해 기능을 만들지 않는다.

문제가 발생했을 때 해당 문제를 해결하기 위해 필요한 기술을 도입한다.

각 Phase마다 문제 상황, 원인 분석, 해결 과정, 결과를 기록한다.

최종적으로 일반적인 Spring 백엔드에서

운영 문제 해결과 확장 과정을 거쳐 AI-native backend까지 발전시키는 것을 목표로 한다.

## 8. API 품질과 현재 보장 범위

- 요청 DTO의 Bean Validation과 PATCH의 수동 검증을 적용한다. 비즈니스 규칙 위반은 BusinessException으로 표현하고 GlobalExceptionHandler가 ProblemDetail로 응답한다.
- 입력·JSON·경로 오류는 400, 권한 위반은 403, 조회 대상 없음은 404, 중복·상태 충돌은 409이다. JWT 필터의 401은 로그인 실패의 ProblemDetail과 응답 경로가 다르다.
- 현재 정상 HTTP 응답은 생성·삭제를 포함해 모두 200이며 삭제 본문은 비어 있다. 201·204는 적용하지 않았다.
- Swagger/OpenAPI에 Bearer 인증을 정의하고 공개 업무 API 4개의 인증 요구를 해제한다. 현재 문서 경로는 공개이며 운영에서 비활성화 또는 접근 제한이 필요하다는 것은 후속 권고다.
- 테스트는 인증·인가·입력·오류 계약·부분 수정·DB 반영과 거래 트랜잭션을 검증한다. 동시 요청의 정합성이나 성능 목표 달성까지 보장하지 않는다. 실행·검증 근거는 [개발환경](development-environment.md)을 참고한다.
